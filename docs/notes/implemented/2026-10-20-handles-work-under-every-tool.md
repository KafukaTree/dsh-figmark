# Note: 缩放手柄在任何工具下都要能拖

Status: implemented

## Problem

用户报「改变大小无法拖动」。复现出来的是一个精确的、百分百必然的陷阱：

`src/client/Canvas.tsx` 的 `beginGesture` 里有一行

```ts
if (tool !== 'select') return
```

本意是「绘图工具下，按在已有标注上只选中、不拖走」，这条规则本身是对的——否则在箭头上起笔会变成拖动那个箭头。但它同时把**缩放手柄**也一起挡掉了。

而点「标注」按钮之后，工具栏的默认工具是 `arrow`（`AnnotatorBody.tsx:191` 的 `useState<Tool>('arrow')`），不是 `select`。于是最常见的进入路径就是：

1. 点「标注」→ 工具是箭头
2. 选中一个已画的框 → 控制框和 9 个把手**正常画出来了**，鼠标移上去**光标也变成缩放箭头**（`cursorFor(handle.id)`）
3. 按下去拖 → 什么都不发生

手柄是可见的、光标是对的、拖动无效。这是最糟的一类 bug：界面上每一处提示都说「这里可以拖」，只有实际行为否定它。用户不会想到「我得先切到选择工具」——因为没有任何东西提示存在这么个前提。

用真实浏览器事件复现（不是 jsdom），五个工具各拖一次 `nw` 把手：

```
select  nw 96.5,96.5 -> 66.5,66.5  (moved 30px)
arrow   nw 96.5,96.5 -> 96.5,96.5  (moved 0px)   ← 默认工具
rect    nw 96.5,96.5 -> 96.5,96.5  (moved 0px)
pen     nw 96.5,96.5 -> 96.5,96.5  (moved 0px)
text    nw 96.5,96.5 -> 96.5,96.5  (moved 0px)
```

## Decision

**把手是控件，不是内容，所以 `tool` 管不到它。** 判断条件收窄成：

```ts
const control = handle !== undefined && handle !== 'label'
if (!control && tool !== 'select') return
```

`label` 被排除，是因为拖说明牌在语义上就是移动内容本身（text 类移动标注、stroke 类移动牌子），和拖图形是一回事，应该继续跟着工具走。

理由：把手只在**选中**的标注周围画出来、只有 7 像素宽、还带缩放光标。按在一个 7 像素宽、显示缩放光标、长在选中框角上的白方块上，除了「缩放这个」没有第二种解释。把它做成依赖当前工具，等于让界面撒谎。

其余一切不变：图形自己的命中区、说明牌，照旧是内容而不是控件——绘图工具下按在上面仍然只选中，不会在标注底下开始一笔。

## Verification

真实浏览器（Playwright + 真实鼠标事件）复验：

- 五个工具拖 `nw` 把手：全部 `moved 30px`
- `arrow` 工具下拖旋转把手：`196.5,74.5 → 325.97,119.72`，标记真的转了
- `select` 下沿描边拖图形：移动 36px；`arrow` 下同样动作：0px —— 语义边界保住了

`pnpm run check` 三门槛全绿：typecheck / oxlint 0 warning / 27 test files、621 tests / 每文件四项覆盖率 100%（`Canvas.tsx` 100%）。

新增 3 条测试钉住：五个绘图工具下 resize 都能用、`arrow` 下旋转能用、绘图工具下按图形本身仍然不移动（防止为了修手柄而把工具语义一起放开）。

## Alternatives considered

- **点「标注」时把工具默认改成 `select`** —— 只掩盖了一个入口，用户切到箭头后又会撞上同一个陷阱；而且「进标注模式后默认是箭头」本身是合理的（多数人进去就是要画箭头）。
- **把手在非选择工具下不画出来** —— 比「画出来但拖不动」好，但仍然要用户自己去猜「为什么框没有手柄了」。而且画出来的框本身还有用（让人看清选中了什么、边界在哪）。
- **让 `tool` 决定手柄能不能用，但在用户第一次拖不动时弹提示** —— 用一次失败换一个提示，不如直接让它能用。
- **把 `label` 也算控件一起放开** —— 那会让「沿着箭头描一遍」变成「把箭头的说明牌拖走」，正好破坏了原本要保护的语义。
